2. HOW THE PLATFORM USES THE VM
===========================================================================
Two machines:
  CONTROL VM   small e2-micro, always on. Serves the web page, keeps the
               job queue, and is the ONLY thing that can start the worker.
  WORKER VM    your L4. OFF whenever there is no work.

Automatic ON / OFF
  ON      A user finishes uploading. The control VM queues the job and calls
          the Compute Engine "start" for this one VM. Ten uploads at once
          still make one start. Starts are at least 120 s apart and at most
          6 per hour.
  WORK    The VM boots, a system service checks the machine, then asks the
          control VM for jobs one at a time and uploads results to the bucket.
  OFF     When the queue has been empty for the idle wait (3 minutes by
          default), the control VM tells the worker to shut down. The worker
          exits with code 75 and a systemd command powers the machine off.
          The worker itself has NO Compute permission.
  SAFETY  Every 60 s the control VM compares what it expects with what
          Compute Engine reports ("get"). It stops a VM that booted but never
          became ready, one running with no work and no worker contact, and
          one told to shut down that did not. A job whose worker dies is
          retried from its checkpoint.
  RESULT  The control VM needs exactly three Compute permissions, on this
          one VM: get, start, stop.

Website and data
  - The control VM serves the web page and API. It is published through an
    outbound-only Cloudflare tunnel, so no inbound firewall rule is needed
    for the web.
  - The worker talks to the control VM over the private network (tcp:8000)
    using a Google-signed identity token. No keys are exported anywhere.
  - Uploads and outputs live in one private bucket. Nothing is public.

Reference build (proof it works)
  Running since 17 Oct 2026 in a separate test project (alphatitans-cloud-1017).
  Measured: boot to ready in 51 s; a 30-second video in about 7 minutes on an
  8-CPU VM. Confirmed live: the control VM needed only get / start / stop on
  the worker; the "act as service account" permission was NOT needed for it.

Honest notes
  - Today's video pipeline encodes on the CPU (libx264). The L4's GPU is used
    only if we later adopt NVENC (a code change not yet made). The platform
    runs the same either way.
  - The L4 costs about 0.71 USD per hour (g2-standard-4, us-central1; please
    check your region), and only while it is running.
  - The platform STOPS this VM automatically when idle. Please confirm the L4
    is dedicated to this, or that stopping it is acceptable.

4. PLAN A (RECOMMENDED) - DETAILS
===========================================================================
4-A. ONE-TIME SETUP BY THE PROJECT OWNER (nothing here is granted to us)

   1. Enable APIs: compute, storage, iamcredentials.
      Optional: aiplatform (only for AI-made music, see step 10).
   2. Create two service accounts: at-control and at-worker. No keys.
   3. Create one private bucket: uniform bucket-level access, public access
      prevention ON.
   4. Give each service account Storage Object Admin on THAT bucket only.
   5. Create the custom role atWorkerOperator with exactly:
        compute.instances.get, compute.instances.start,
        compute.instances.stop
      Bind it to at-control on the L4 instance only (instance-level policy,
      not project level). We can send the role file.
   6. On the L4: stop it, attach service account at-worker with the
      cloud-platform scope, start it. If you want to keep its current
      service account, tell us which; it must reach only our bucket.
   7. Create the control VM (e2-micro, 30 GB standard disk) in the same
      zone and VPC as the L4, running as at-control. We can send the exact
      command.
   8. Firewall: allow tcp:8000 only from network tag at-worker to tag
      at-control; allow SSH only from Google's IAP range 35.235.240.0/20.
   9. Allow an external IP on the control VM (the web tunnel connects
      outward from it), or tell us if policy forbids it.
  10. Optional AI music: enable Vertex AI and give at-worker
      roles/aiplatform.user. This is project-wide and costs about 0.08 USD
      per track. It can be left out: the platform then composes music in
      code.
  11. Set a budget alert on the project.

5. PLAN B - IF WE SET EVERYTHING UP OURSELVES (not recommended)
===========================================================================
Instead of the owner steps in 4-A, our account would need these (or
equivalent custom roles), which are broad:
   roles/serviceusage.serviceUsageAdmin     enable APIs
   roles/iam.serviceAccountAdmin            create service accounts
   roles/iam.roleAdmin                      create atWorkerOperator
   roles/storage.admin                      create the bucket, set its IAM
   roles/compute.instanceAdmin.v1           create/change/start/stop VMs
                                            (this can also DELETE VMs)
   roles/compute.securityAdmin              create firewall rules
   roles/iam.serviceAccountUser             attach service accounts to VMs
   plus the ability to edit IAM policy on the L4 instance and the bucket.
Plan A needs far less, which is why we recommend it.
